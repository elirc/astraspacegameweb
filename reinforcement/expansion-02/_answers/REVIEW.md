# Sealed capstone and review notes

Require an actual source trace from event selection through the effect's commit before accepting a concurrency claim. Reject a patch that changes scheduling and transactional ownership together without separate acceptance cases. Ask for a same-time fixture and a two-world fixture.

For operational work, require the heartbeat's writer, its meaning, and its clock domain. Reject a healthy default for missing telemetry and an alert justified only by a number copied from the exercise. Require an example where request success coexists with stale game state, and a written next diagnostic step that follows from that distinction.

## Assess a learner's explanation

Ask for the actual input and observable result, then change one assumption. A strong explanation adapts the test or identifies a missing product decision. A weak explanation repeats the reference implementation without explaining why its boundary belongs there.

Do not award runtime evidence for a written plan. Keep “source supports this,” “model reproduced this,” and “application reproduced this” as separate statements. If an existing implementation already handles a scenario, the useful contribution may be a test and a clearer contract rather than another fix.
