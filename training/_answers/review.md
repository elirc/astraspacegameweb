# Model review: Warband, "The Crownlands" (staff-level, ranked by production severity)

Evidence is at `3ef7432`. **[RUN]** = verified by running something on 2026-09-24 (details in `_answers/evidence/runs-2026-09-24.md`).
**[AI-smell]** = typical of old AI-generated code: config or docs that look complete but aren't wired, swallowed errors, hard-coded fallbacks.

Credit where due, before the list: the engine's crash safety is real ([RUN] `tools/sim/chaos.ts` passed: 8 workers, 2 killed, a backend terminated,
Postgres restarted, Redis flushed, final state identical to the serial reference). Refresh-token rotation with reuse detection is correct
(`application/auth.ts` `post_api_auth_refresh`). `docs/verification.md` honestly reports the failed load gate. This review is about **operating** it.

## Critical

1. **Every production process runs migrations at boot, and the checksum is over raw bytes.** `apps/server/src/index.ts:16` `await initialize()` →
   `packages/db/index.ts:144-148` `sha256(sql)` vs `schema_migrations`. Any byte change to an applied file (a comment, **CRLF line endings**) crash-loops
   every role. [RUN] The same commit checked out via a worktree on this machine (`core.autocrlf=true`, no `.gitattributes`) has CRLF `.sql` files.
   The LF main tree then refuses a DB migrated from it: `Applied migration was modified: 001_initial.sql`. The `Dockerfile` does `COPY . .`, so an image
   built from a Windows checkout fails against a Linux-migrated DB. *Prod:* a full outage from a no-op change. Fix: `.gitattributes *.sql text eol=lf`,
   hash normalized text, a one-shot migrate job, and roles verify-only. (→ INC-004)
2. **No image identity, so no real rollback.** `compose.production.yaml:3` `build: .` in the shared anchor; no `image:` tag. The runbook
   (`docs/runbooks/deployment.md` step 1) demands "one immutable image digest for all roles". The compose file can't express that. *Prod:* rollback means
   rebuilding old source under pressure. [AI-smell: the runbook claims a property the config can't have.]
3. **Alerts go nowhere, and "everything is down" is not an alert.** `infra/prometheus.yaml` has no `alerting:` block and there's no Alertmanager service.
   `infra/alerts.yaml` has no `up == 0`/`absent()` rule. Every rule needs a successful scrape, so a total outage is silent. The architecture doc says
   "Grafana dashboards and alert rules are included". True, but they page no one. [AI-smell]

## High

4. **Resolver contention is invisible.** `application/engine.ts:805-807`: the resolver transaction runs with `maxAttempts = 1`, and `WB_BUSY`/`40001`/`55P03`
   are caught and `return 0`. `packages/db/index.ts:80` only counts WB_BUSY exhaustion when `maxAttempts > 1`. [RUN] During a 150/s run on `main`,
   `resolver_errors` and `lock_retries` stayed 0 while Tempo showed `pg.query:ROLLBACK` spans and `pg_stat_database` showed 163–179 rollbacks per
   6,000-arrival drain. *Prod:* the most important scaling failure mode has no metric. (→ INC-001)
5. **The random candidate window is load-bearing and undocumented.** `engine.ts` `resolveDue`: `start = random…` is what keeps concurrent resolvers
   from colliding. Nothing says so. A plausible "fairness" refactor destroys multi-resolver throughput. [RUN] 91–115 s → 151–154 s. (→ INC-001)
6. **Histograms clip at their top bucket, and the dashboard can't show it.** `metrics.ts:19` lag buckets end at 60 s; `metrics.ts:39` resolver buckets end at 30 s.
   [RUN] Lab 0 on `main`: `lag_p99 = lag_p50 = 60.0` while the oldest event was 111 s; `resolver_transaction p99 = 30.0`. *Prod:* on-call reads "60" as
   the lag when it's "≥ 60". The alert survives only because of its `oldest_event` clause. (→ INC-002)
7. **Liveness, readiness and dependency health share one endpoint.** `game.ts` `get_api_health` is `SELECT 1`, used by Caddy `health_uri`
   (`infra/Caddyfile:7`), the compose healthcheck and every drill. A Postgres failover makes all API instances unhealthy at once, so Caddy has no upstream
   and returns 502 for the SPA too. It's also the obvious place someone will add Redis. (→ INC-005)
8. **The error-rate alert measures probes, not players.** `alerts.yaml:19` counts every route, including `/api/health` (Caddy every 10 s per instance +
   docker every 15 s) and `/metrics`. During an edge-level outage, the 5xx are generated by Caddy and never reach the app histogram. `clamp_min(…, 1)`
   under-states the ratio below 1 req/s. [RUN] a Redis-less health probe was recorded as `route="/api/health",status="500"`.
9. **Connection budget exceeds a default Postgres.** `packages/db/index.ts:19` `max: 16` per process × 7 processes (api×2, resolver×3, relay, sidejobs) = 112,
   plus migrations and admin tools. Stock Postgres `max_connections` is 100. *Prod:* `too many clients` under load, first in the resolvers. No pool metrics
   (`pool.totalCount/idleCount/waitingCount`) are exported.
10. **Traces are fragmented into per-query roots.** `bootstrap.ts:14` auto-instrumentation with no custom spans. Resolver/relay/NPC loops run outside any span.
    [RUN] Tempo, 2 min on `main`: ≥ 1,000 resolver traces (search cap), 850 of them a lone `pg.query:SELECT`, with BEGIN/COMMIT/ROLLBACK as separate
    traces. No sampler is configured, and `/metrics` scrapes are traced too ([RUN] 125 of 200 sampled `warband-api` traces were `GET /metrics`, each with 3 pg child spans). *Prod:* you can't follow a resolver batch, and storage fills with noise. The runbook (`stuck-event.md`) says
    "correlate resolver logs by request/trace ID", but resolver ticks have neither. [AI-smell]
11. **Side-job retries never end, and there's no backlog signal.** `sidejobs.ts:130-131`: every 5 s, `dispatch()` calls `prior.retry()` on any failed job,
    restarting its 8-attempt backoff forever. There's no DLQ state, no metric for `side_effects WHERE delivered_at IS NULL`, and no alert. *Prod:* a broken
    SMTP credential becomes a permanent retry storm plus an invisible pile of password-reset emails.
12. **External calls inside DB transactions.** `sidejobs.ts:69-75` holds `FOR UPDATE` and a pool connection across `mail.sendMail` (10 s connect + 15 s socket
    timeouts) and web-push. `index.ts:68` publishes to Redis inside the outbox transaction. *Prod:* a slow SMTP/Redis pins connections from the 16-slot pool.

## Medium

13. **The WS heartbeat hits the DB per socket.** `transport/app.ts:123-127` calls `authenticate(req)` (a session join query) every 5 s per socket. 10k sockets ≈ 2k qps
    of session lookups. It's capacity that nobody has measured.
14. **No WS metrics at all.** Only a gauge of *registered* sockets (`index.ts:117`). [RUN] `/api/ws` upgrades don't appear in `warband_http_request_seconds`.
    There are no open/close/close-code or hint-delivery counters, so realtime regressions are found by players. (→ INC-003)
15. **`resolver_transaction_seconds` measures ticks, not transactions.** `index.ts:45` starts the timer for every 50 ms tick, including empty and busy ones.
    At idle the "p99 transaction time" is a no-op poll time. Label by outcome or observe committed ticks only.
16. **Counter semantics on gauges.** `metrics.ts:65-80`: `warband_lock_retry_exhaustions_total` and `warband_lock_retries_total` are `Gauge`s named `_total`, fed by
    in-process counters. `increase()` in `LockRetriesExhausted` works by accident (reset detection). The type metadata is wrong for tooling and recording rules.
17. **Scrape-time SQL on every replica.** `metrics.ts:84-122`: three global `count(*)`/`min()` queries per scrape per process (7× redundant), on the app pool.
    Under DB saturation the scrape slows or fails, and exactly the backlog gauges disappear during the incident they exist for.
18. **Deploys take the exclusive world lock seven times.** `initialize()` starts with `worldLock(tx)` (exclusive) in every process. While any process is migrating
    or just checking checksums, simulation (shared lock) blocks. Rolling restarts stall resolvers. [RUN] While restarting 5 roles on a loaded laptop,
    `pg_stat_activity` showed three processes waiting on `pg_advisory_xact_lock(7139,1)` behind a fourth that sat `idle in transaction` inside `initialize()`,
    and none of the roles listened on HTTP for minutes.
19. **The chaos/outage drills hide their own failure reason.** `tools/sim/redis-outage.ts` spawns the server with `stdio: 'ignore'`. [RUN] It failed once cold on `main`
    and passed on retry, with no diagnostics. This is exactly how a flaky label hides a real regression. (→ INC-005)
20. **Grafana/Tempo in prod are unauthenticated internals with no retention or budget review.** Tempo has `block_retention: 168h` on a local volume, no
    `metrics_generator` (so no RED metrics from traces), and Prometheus doesn't scrape itself, Tempo, Caddy, Postgres or Redis. That's blind to dependency saturation.
21. **The load gate has no path to green.** `docs/production-work.md:23` shows 1,000 arrivals/s unchecked. [RUN] On this laptop, 3 resolvers sustain ~110–120 events/s
    before lag grows without bound. There's no capacity model (events/s per resolver vs DB CPU), so "more hardware" is a guess. The docs are honest about it.

## Low

22. **Hard-coded JWT fallback.** `transport/app.ts:47` `'local-only-warband-secret-change-before-deployment'`, guarded by a ≥32-char check only when
    `NODE_ENV=production`. A staging box with `NODE_ENV=staging` runs with a public secret. [AI-smell, mild]
23. **Secrets on disk.** `.env` and `infra/runtime/metrics_token` exist in the working tree. Both are git-ignored and not tracked (`git ls-files` shows only
    `.env.example`). Just keep it that way. (Location reported only.)
24. **`/metrics` is open outside production.** `metrics.ts` only checks the bearer token when `NODE_ENV === 'production'`. That's acceptable locally, but combined
    with 22 it means any non-prod deployment leaks internals.

## Top 3 to fix first

(1) migrations out of app startup + byte-normalized checksums + `.gitattributes`; (3) Alertmanager + `up`/`absent` rules + an edge probe; (4) resolver tick-outcome metrics.
The rest follow from having an SLO (ladder M1).
