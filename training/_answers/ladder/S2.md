# S2 reference: path to 1,000 arrivals/s

Grounding numbers (this laptop, `main`): ~110–120 events/s with 3 resolvers; per-event write cost dominates (M2 profile). The target is ~1,000 arrivals/s,
i.e. ≥ 2,000 events/s including returns, so roughly **17× today's box**. No single lever gets there. The design has to stack them and measure each.

## 1. Partitioning without collisions
- Today concurrency comes from a *random* window (INC-001) plus try-locks. Replace it with **shard leases**: `shard = hash(target village) % S` (S ≫ resolvers,
  e.g. 64). Each resolver takes session-level leases `pg_try_advisory_lock(7140, shard)` for its share and resolves its shards oldest-first.
- Causal rules still apply *across* shards: morale reads player-wide points, support links stations to homes, conquest redirects returns. Keep
  `lockCausalComponent` as the correctness guard. Leases only reduce *who tries*, so collisions become rare instead of systematic. Cross-shard components
  (tribe wars) still serialize, and that's correct.
- Lease holder SIGKILLed: session advisory locks release on disconnect. Transaction rollback leaves events pending, so another resolver takes the shard on its
  next lease scan. Note that session locks are **incompatible with PgBouncer transaction pooling** (M4).

## 2. Per-transaction cost
- `event_journal.context.reads` stores every query's full result rows for replay. It's the largest single cost (15 s of 78 s). Options: store row hashes and
  `village_snapshots` references, and keep full reads for a sampled 1% plus all conquests. Replay then verifies the *hash* chain and re-reads snapshots. Loss:
  byte-exact replay of arbitrary old events without snapshots. Write that into ADR 003.
- `reports` per battle for both players: keep. It's the product. Batch across the tick (already bulk). Consider `jsonb` compression (`tools/sim/profile-compression.mjs`
  exists: check the result) or TOAST tuning.
- Plan query cost scales with **all** due events (`causality.ts` `sql` has no component filter). Filter by the initial villages' neighbourhood first and fall back
  to the full graph only when support links exist.

## 3. Database
- WAL volume: journal + reports + village updates. Measure `pg_stat_wal`. `synchronous_commit=off` for resolver transactions is tempting (bounded loss of
  <1 s of *resolutions*, which re-run deterministically from pending events!). That's a real, defensible lever here because resolution is replayable. Say so explicitly.
- `villages` fillfactor 70 + HOT (migration 009) is a hypothesis in `docs/architecture.md`. Measure `n_tup_hot_upd / n_tup_upd`.
- Time-partition `event_journal` and `reports` by week: cheap retention and smaller indexes. `scheduled_events`: partial indexes on `pending` already keep hot
  indexes small, so partition only if vacuum can't keep up.

## 4. The hour-mark spike
Define the SLO over the **arrival-weighted** lag (M1 SLI). A 60 s spike at 5× that drains within 90 s may be inside budget. Size resolvers for p95 of per-minute
arrival rate, not the peak, and make the spike visible (`oldest_event` rising then falling). Players care about their noble train. A 30 s delay for everyone
at :00 is a product decision: surface it ("the world is resolving the hour") rather than hide it.

## 5. Measurement plan
Dedicated hardware for Postgres, `tools/sim/load.ts` (committed-lag via IPC, which is correct: applied_at-based lag under-reports), ≥ 3 runs, warm cache and
cold cache reported separately, and the chaos drill re-run after every structural change. First implemented step: shard leases or journal slimming, whichever the
profile says is bigger on the target hardware. Success means a before/after with 2+ runs each, not a single green run.
