# J1 reference: side-effect backlog

## Explain-before-touching reference
1. `application/admin.ts` gets a use case `get_api_admin_side_effects_summary`. The route goes in `transport/admin.ts`. The gauges live in
   `apps/server/src/metrics.ts` and are **set** from `sidejobs.ts` (`server` layer, which may import `db`). `eslint.config.js`: transport → application only;
   application → db allowed; transport → db forbidden (enforced by `tools/check-boundaries.mjs`).
2. DB rows → aggregate → DTO `{kinds:[…]}` → JSON (the `preSerialization` hook adds `server_now`) → admin UI. Separately, sidejobs timer → gauge → `/metrics` → Prometheus.
3. Failures: slow DB (keep it off the scrape path), label explosion from arbitrary `kind` strings (hence the allow-list), a non-admin (the `/api/admin` prefix
   hook in `createAdminUseCases().addHook_preHandler` → 403; anonymous is stopped earlier by the `onRequest` authenticate hook → 401).
4. Unit (mapping) needs no DB. Integration needs Postgres (`API_TEST_DATABASE_URL`, `*_test`).
5. Scrape-time `collect()` is fresh but runs on every replica and fails with the DB (Lab 0: backlog gauges are exactly what you need when the DB is struggling).
   A timer in the one role that owns side effects is cheaper, and the staleness is bounded by the 5 s dispatch interval.

## Reference implementation sketch
```sql
SELECT CASE WHEN kind IN ('email','push') THEN kind ELSE 'other' END AS kind,
       count(*)::int AS pending,
       coalesce(extract(epoch FROM now()-min(created_at)),0)::float AS oldest_seconds
FROM side_effects WHERE delivered_at IS NULL GROUP BY 1;
```
`EXPLAIN` uses `side_effects_pending` (a partial index on `id WHERE delivered_at IS NULL`). A full table scan here would be a finding.
In `dispatch()` (`sidejobs.ts`), after the existing query, set `sideEffectsPending.set({kind}, n)` for **every** allowed kind, including 0.
Otherwise a kind that drains to empty keeps its last non-zero value forever.

## Grading notes
- Missing the "reset to 0" case is the most common bug. Ask them what the gauge shows after the backlog clears.
- They should notice that the sidejobs retry loop (`prior.retry()` every 5 s) means a broken SMTP never lets `oldestSeconds` fall. That's good material for the alert:
  `max(warband_side_effects_oldest_seconds{kind="email"}) > 900 for 10m`.
- The live check (stopping Mailpit) is the point of the ticket. Accept no PR without the PromQL output.
