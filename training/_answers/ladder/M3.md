# M3 reference: scrape-safe backlog gauges

1. `prom-client` `Registry.metrics()` awaits every metric's `get()` (which calls `collect`) with `Promise.all`. One rejected async `collect()` rejects the whole
   `registry.metrics()`, so the `/metrics` handler in `metrics.ts` throws and Fastify returns **500 for the entire scrape**. `up` becomes 0 for that target. The
   *HTTP* and *process* metrics vanish together with the backlog gauges, precisely during a DB incident. (Verify with `docker pause` on Postgres: the scrape
   hangs until pg's query waits out, then fails.)
2. `max()` over 7 copies hides a stale or failed copy only if another copy still reports. If all fail, the series disappear and `max(...) > 10000` evaluates to
   empty. That isn't an alert, and it's why `absent()`/freshness rules are needed.
3. Scrape-time is fresh but its cost and fragility scale with replicas × scrape rate. A timer in one role is cheap and isolated, but stale by up to one interval,
   and needs a freshness signal.
4. Implementation: in the `sidejobs` role (one per deployment), a 5 s timer runs the three queries in one `SET LOCAL statement_timeout='2s'` transaction on a
   dedicated `new pg.Pool({ max: 1 })`, so it never competes with delivery work. It sets the gauges plus `warband_backlog_sample_timestamp_seconds`.
   Other roles don't register the gauges. Alert `BacklogSampleStale: time() - max(warband_backlog_sample_timestamp_seconds) > 60 or absent(...)` for 2m,
   warning. `EventLagHigh`'s oldest-event clause uses the same gauge. When the sample is stale, *StaleSample* fires instead, so there's no double page.
5. Expected measurement shape: scrape duration of the API role drops to single-digit ms (no SQL). The sidejobs role's sample takes ~tens of ms at 8k pending
   on this box (partial indexes `events_due`, `outbox_pending`).

Grading: the "role is down → stale alert" case is required. Keeping `async collect()` "but with a timeout" on every role is only a partial answer.
