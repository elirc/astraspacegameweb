# M2 reference: resolver capacity curve

Reference numbers from this laptop (2026-09-24; Docker Desktop Postgres 16 on the same machine as the Node processes). Yours will differ. Grade the method.

| Config (main) | Measurement | Result |
|---|---|---|
| 3 resolvers, steady 150 arrivals/s | resolved/s, including returns | 110–120 events/s; backlog grows without bound |
| 1 resolver, 6,000-arrival backlog | drain time (incl. ~15 s start) | 127 s, 115 s |
| 3 resolvers, same backlog | drain time | 115 s, 91 s |
| 1 resolver in-process profile | per tick | ~522 events/tick, 23 ticks, 78 s |

Profile (one resolver, 6,000 arrivals → 12,000 events): `INSERT INTO event_journal` 15.0 s, `INSERT INTO reports` 11.6 s, `INSERT INTO scheduled_events` 7.6 s,
causal plan `SELECT` 6.6 s over 46 calls, `INSERT INTO outbox` 6.2 s, `UPDATE villages` 4.9 s.

## Expected conclusions
1. **One unit of work = one causal component drained in one transaction.** `resolveDue` → `lockCausalComponent` (a shared world lock, 2× `plan()` queries,
   `try_component_locks`) → `drain` (in-memory event loop, then 6 bulk statements at the end).
2. **Per-event cost dominates, and it's write volume:** `event_journal` stores before/after state *and the read trace* (`reads` in `resolveEvent`) for every
   event. That's the replay feature's price (`docs/adr/003-replay-evidence.md`). Reports and new events come next. Planning is the fixed per-transaction
   cost, ~8% here, and it grows with backlog size because `plan()` scans **all** due pending events (`causality.ts` `sql`: `e.due_at<=$2`, no component filter).
3. **Scaling 1 → 3 barely helps on this box** (≈ 120 s → ≈ 100 s): Postgres CPU and WAL are the shared bottleneck, and concurrent resolvers add rollbacks
   (163–179 per drain) that each re-pay planning. More resolvers against the same DB is not a lever until the per-event write cost falls.
4. **Batch size:** bigger batches amortize planning but hold locks longer and make collisions costlier. Expect a shallow optimum. The measurement matters more than the number.
5. **How to tell where time goes:** Postgres CPU (`docker stats`), `pg_stat_activity.wait_event_type` (Lock vs IO vs NULL = CPU), `pg_stat_statements`
   total_exec_time, Node event-loop lag (`warband_nodejs_eventloop_lag_seconds` from `collectDefaultMetrics`).

## Grading
- Reject single-run numbers. The same config gave 104 s and 252 s in two runs here.
- Reject "the bottleneck is the database" without a statement-level breakdown.
- A strong answer proposes shrinking `event_journal.context.reads` (e.g. store hashes plus a sampled full trace) and predicts the gain from the profile share.
  That leads into S2.
