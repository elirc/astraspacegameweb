# J3 reference: resolver tick spans

1. OTel context propagates through AsyncLocalStorage. A `setInterval` callback starts with the ROOT context, so every auto-instrumented `pg` span has no parent
   and becomes a new trace. [RUN on 2026-09-24] 2 minutes of resolver traffic → ≥ 1,000 traces (search cap), 850 of them a lone `pg.query:SELECT`, plus
   separate BEGIN (32), ROLLBACK (25) and INSERT (16) roots.
2. Add `resolveDueDetailed(): Promise<{ resolved: number; outcome: 'committed'|'empty'|'busy' }>` in `engine.ts`. Keep `resolveDue()` returning a number
   (`tools/sim/worker.ts`, `tools/sim/load.ts` and the chaos harness call it). Errors are thrown as today and recorded with `span.recordException` + status ERROR.
3. Volume: ~20 ticks/s × 3 resolvers = 60 root spans/s at idle, each with 1–3 child queries. That's ~150 spans/s just to say "nothing to do". Options: don't
   create a span when the candidate query returns 0 rows (start the span after it), or sample empty ticks at 1%. Busy ticks are rarer and diagnostic: keep them all.
4. Risk: `startActiveSpan` with an async callback. If the code forgets `span.end()` on the error path, spans leak. Use try/finally. And if the wrapper
   swallows exceptions it would *hide* errors. The `.catch` that increments `resolverErrors` in `index.ts` must still see them.

Dependency note: `@opentelemetry/api` is not importable from the app today (pnpm strict layout: only `sdk-node`, `auto-instrumentations-node` and
`exporter-trace-otlp-http` are top-level in `node_modules/@opentelemetry/`). Add it as a direct dependency with the version the SDK already resolves, and
check that `pnpm why @opentelemetry/api` shows one copy. Two copies means two global tracer registries and **no spans**. That's the classic silent failure.

TraceQL: `{ name = "resolver.tick" && span.warband.outcome = "busy" }`. On `main` with 3 resolvers at 150/s, expect busy ticks in the hundreds per drain
(the DB showed 163–179 rollbacks per 6,000-arrival drain). On the INC-001 branch, 3–4× that.
