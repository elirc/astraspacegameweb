# S1 reference: release process with a rehearsed rollback

UNVERIFIED as a whole: the reviewer did not run a production-compose rehearsal (it needs real secrets/VAPID/SMTP values). The pieces it depends on are
verified: INC-004 crash-loops as described, and `close()` in `index.ts` sends 1012 and awaits in-flight work.

## Reference design (state machine)

```
build(sha) → push image warband:<sha>          # CI, once; all roles use this tag
preflight  → compose config validates; image digest recorded; SLO burn currently < 1×
migrate    → one-shot `migrate` service: `node tools/migrate.ts` with the NEW image
             • fails if an applied file's normalized hash differs (INC-004); nothing else has changed yet → abort is free
api-canary → start api-new alongside api-old (override file with a second service name, same network)
             • readiness (DB + migrations verified + not closing) → add to Caddy upstreams (reload Caddyfile with both)
             • 5 min bake: command SLO fast-burn (M1) not firing, 5xx on /command < 0.5%, WS opens ≈ closes
api-swap   → remove api-old from Caddy; SIGTERM api-old (1012 to sockets; clients reconnect with backoff 1 s…)
resolvers  → one at a time: SIGTERM, wait for exit ≤ 60 s (stop_grace_period), start new, 60 s bake on lag SLO + oldest_event
relay, sidejobs → replace (singletons; a gap of a few seconds only delays hints/mail)
done       → record release; keep previous tag for 7 days
rollback   → RELEASE=<prev> for all roles, same order; the schema stays (expand-only)
```

## Gates and triggers
- Auto-rollback during api-canary/resolvers if **any**: M1 page-level burn for 2 consecutive evaluations; `up{role=…}==0` for a new target;
  5xx ratio on `/api/villages/:id/command` > 2% for 2 min.
- Bad release vs bad evening: compare **new vs old** side by side during the canary (the same traffic split through Caddy `lb_policy round_robin`). A regression
  is new-minus-old. If both degrade, it's load, and you pause the rollout rather than roll back.

## Answers to the pressure points
- Mixed versions: `/api/state` JSON must only *add* fields; the WS hint format (`{...outboxRow, server_now}`) must stay parseable by old clients (the client only
  checks `type`); idempotency keys live in Postgres, so a retried command hits the same row whichever version answers.
- App rollback after a successful migration is safe **because migrations are expand-only** (curriculum 07). It isn't safe after a contract step (dropped
  column) or a data rewrite. Those ship only after the rollback window.
- `/api/health` for routing must be *readiness* of this instance only (INC-005). Liveness goes to the restart policy.
- `stop_grace_period: 60s`: `close()` waits for `resolving`, `relaying` and `thinking` plus `stopJobs` (BullMQ worker close, 20 s deadline). The resolver
  transaction itself is bounded by `lock_timeout 5s` per statement, but a large `drain` can exceed 60 s under a big backlog. SIGKILL is still safe (rollback) but
  wastes work. Lower `RESOLVER_BATCH_SIZE` before draining a resolver in a backlog.

## What's not covered (must be listed)
Postgres/Redis upgrades, secrets rotation (JWT rotation logs every player out: no `kid` support), Caddy/cert changes, single-host failure (the whole
topology is one Docker host), and Prometheus itself being down during a release (then the gates must fail closed: no data means no promotion).

## Rehearsal B expectation
The INC-004 image fails at **migrate** in seconds. No player-facing container is touched. Time to abort is under 1 min, versus the outage in INC-004.
