# J2 reference: WebSocket lifecycle metrics

1. A socket's life: the handler in `transport/app.ts` (`app.get('/api/ws', { websocket: true }, …)`) → `set.add(socket)` → closes come from the client, from the
   heartbeat catch (`close(4001, 'Session revoked or expired')`), from the `expiry` timer at JWT exp (`4001 'Session refresh required'`), from the shutdown in
   `index.ts close()` (`1012`), and from network loss (`1006` seen by the server as abnormal closure).
2. Only roles that register `/api/ws` and accept traffic (`all`, `api`, `ws`) produce non-zero values. Resolvers expose the metric names with zeros, or not at all if
   they're created lazily. Prefer creating them in `metrics.ts` so series exist everywhere.
3. Cardinality per instance: `opened` 1 + `closed` ≤ 7 codes + `hints` 2 = ≤ 10 series.
4. (a) Deploy: a burst of `1012` closes, then an equal burst of opens (the client's backoff starts at 1 s). (b) Redis outage: WS sockets stay open, `hints_total`
   flatlines because the subscriber gets nothing, so opens and closes are *unchanged*. That's why hint counters matter. (c) The backoff loop:
   opens ≈ closes at 1/2/4/…/30 s intervals per client, a sawtooth.

`no_socket` across 2 API replicas is **expected**: each instance receives every Redis message and only one holds the player's socket. The meaningful
signal is `sum by (player)` delivered == 0 while the player has sockets, which you can't express cheaply. So alert on the *ratio*
`sum(rate(delivered)) / sum(rate(no_socket))` changing sharply after a deploy, not on its absolute value.

Tests: `app.injectWS('/api/ws', { headers: { cookie } })` needs an authenticated cookie. Reuse the guest-auth helper pattern from `tests/api.integration.test.ts`.
Grading: reject unbounded `code` labels. Reject counters incremented in the heartbeat. Ask how they verified 1012 (restart the api role in Lab 0).
