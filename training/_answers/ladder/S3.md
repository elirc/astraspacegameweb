# S3 reference: catch-up after a 6-hour resolver outage

UNVERIFIED rehearsal numbers (the reviewer did not run the 60k-event drill). At ~110 events/s on this laptop, 60k events take ≈ 9 min. 2.1 M events on
equivalent hardware would take ≈ 5.3 h, which is itself the headline: **catch-up takes about as long as the outage unless capacity is added**.

1. **Order:** `drain` orders by `(due_at, id)` inside the locked component, and `lockCausalComponent` makes a component's history resolve in one place. Global
   order isn't required, only per-component order. Two resolvers can't interleave one component (the try-locks). Events at 07:00 in component X can commit before
   01:00 events in unrelated component Y. That's fine and faster.
2. **Protect commands:** a command drains its whole component first, so an entangled player's first click after the outage pays for hours of history. Reads too:
   `get_api_state` drains when `needs_drain`. Recommended: a **command drain budget**. If the component has more than N due events (cheap count via
   `events_village`), return **409 "the world is catching up on your region, try again in a minute"**, and prioritize that component in the resolvers
   (a `priority_villages` table the resolver reads first). Serve reads from the MVCC snapshot without draining during catch-up mode, with a banner. Quantify: API
   p95 with and without the budget in the rehearsal.
3. **Levers at 07:00:** pause NPCs (`runNpcBatch` competes for the same locks; set via the admin NPC controls), pause side jobs except password reset, keep
   `RESOLVER_BATCH_SIZE` moderate (big batches → long transactions → more collisions and slower shutdowns), and add resolvers **only** if M2 showed the DB has
   headroom (on this laptop it didn't). More replicas can be slower (INC-001).
4. **Players:** 180k battle reports → 180k+ outbox rows (relay: 500 per 100 ms ≈ 5,000/s, fine) → incoming-attack pushes for attacks that already landed
   hours ago. Skip pushes whose `due_at` is older than 10 min (the relay only creates push side-effects for `incoming_attack`), and send one digest email per player.
5. **Signals and exit:** `oldest_event` falling linearly (its slope *is* the ETA), `pending_events`, the command 409 rate, and M1's burn (it will be at 100%: silence
   the lag-SLO page with an expiry and a named owner). **Never silence:** `WorldNotAdvancing`, 5xx on commands, `up == 0`. Done = `pending_due == 0` for 10 min
   and API p95 back under 150 ms.

Pressure points:
- The disputed noble train: `event_journal` rows for both events in the target village give `(due_at, id)` order and before/after state. The replay tool
  (`application/replay.ts`, admin range replay) re-executes them. Order is decided by `due_at` then `id`, not by commit time. The `id` came from
  `scheduled_events_id_seq` at *send* time, so ties go to the earlier sender.
- Poison event: the resolver keeps rolling back the same component. Other components continue (try-locks skip it). Follow `docs/runbooks/stuck-event.md`:
  capture the payload, pinned config and snapshots, fix the handler, and never mark it done manually. Add a `warband_resolver_ticks_total{outcome="error"}` alert keyed on
  repetition (from J3/INC-001).
