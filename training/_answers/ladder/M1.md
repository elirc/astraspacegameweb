## Explain-before-touching reference
1. A "bad event" is one committed with `now - due > 2 s` (`committedResolutions` in `metrics.ts`, called from `afterCommit`). Double counting: no. A transaction
   that rolls back never runs `afterCommit` (`packages/db/index.ts`), and retries observe once, on the commit that sticks. But events that **never** commit are
   invisible (hence the guard).
2. The histogram is emitted by whichever process commits the drain: resolvers *and* API instances (commands drain their component). In production `instance` is
   `IP:3001` from `dns_sd` (no `role` label), so aggregate with `sum()` without a role filter.
3. At 150/s this laptop falls behind in seconds, and every committed event after the first ~10 s is late, so the page is correct. A 14.4× burn on a 99% SLO means
   14.4% of battles late for an hour. For a game where a late noble train changes ownership, that's page-worthy. The noble-train spike at :00 (S2) is the case
   to tune: a 5 m window at 14.4× will fire during a 60 s spike only if >14% of *that 5 minutes'* battles were late.
4. Bucket change: series identity (`le`) changes, the old buckets stop, `rate()` over mixed series is wrong for one window. Annotate releases that change buckets.
   Counter resets on restart are handled by `rate()`.
5. 28 d smooths nightly peaks and matches monthly reporting. 7 d reacts faster but makes one bad war night look catastrophic. Most games: 28 d SLO, 7 d review.

## The two traps (both hit by the reference author, which is the point)
1. **Prometheus 3 normalizes `le`.** prom-client exposes `le="2"`, but Prometheus 3.5 stores `le="2.0"`, `"1.0"`, `"5.0"` (while `"0.5"` stays `"0.5"`).
   [RUN] `/api/v1/label/le/values` → `["+Inf","0.001","0.01",…,"1.0","1.5","10.0","2.0",…]`. A rule with `le="2"` is *healthy*, parses, passes a promtool test
   whose fixtures also say `le="2"`, and returns **nothing** live. The first live drill showed `bad5m=None` for exactly this reason. Use `le=~"2|2.0"` (portable across 2.x/3.x).
   The command SLI's `le="0.5"` is unaffected, which makes it worse: one SLI works and the other is silently empty.
2. **`clamp_min(denominator, 1e-9)` pages at zero traffic.** It "avoids division by zero", but 0 / 1e-9 = 0 → `1 - 0 = 1` → a 100% bad ratio when idle. [RUN] the promtool
   idle case **fails** with clamp_min (the page fires) and passes without it. Without the clamp, 0/0 = NaN, and `NaN > x` is false, which is exactly the behaviour you want.
   The existing `ApiErrors` rule uses `clamp_min(…, 1)` for the opposite reason, and that has its own low-traffic distortion (review #8).

## Guard alert
`WorldNotAdvancing: max(warband_oldest_event_seconds) > 60 and (sum(rate(warband_events_resolved_total[2m])) == 0 or absent(warband_events_resolved_total))`
for 2 m. The SLO can't see a stopped resolver, because nothing commits so nothing burns. The M3 caveat applies: if the backlog gauge itself is stale, this is blind too.
