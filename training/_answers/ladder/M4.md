# M4 reference: connection budget

UNVERIFIED on this laptop (the `max_connections=40` reproduction was not run by the reviewer). The reasoning and formula below are checked against the code.

1. Holders per role:
   - **api**: `transaction()` per command (causal drain inside the request can take seconds under backlog), `database.query` for reads, `authenticate()` on
     every request **and every 5 s per WebSocket** (`transport/app.ts` heartbeat), `/metrics` gauges (3 queries per scrape).
   - **resolver**: one long `transaction()` per tick (`resolveDue` → `drain`) plus the candidate `pool.query`, and the gauges.
   - **relay**: one short transaction every 100 ms.
   - **sidejobs**: up to `concurrency: 4` transactions that stay open **across SMTP/web-push calls** (`sidejobs.ts`), the dispatch query every 5 s, the NPC batch every 1 s, and the gauges.
2. `pg.Pool` queues callers when `max` is reached. The default `connectionTimeoutMillis` is 0 (wait forever), so requests hang rather than fail. On the server
   side, exceeding `max_connections` gives `FATAL: sorry, too many clients already` (SQLSTATE 53300) on connect.
3. A resolver does one transaction at a time (the `resolving` guard in `index.ts`). It needs ~2–3 connections: the transaction, the candidate query, a scrape.
   Giving it 16 only lets idle connections pile up.
4. Formula: `Σ_roles replicas × pool_max + tools (migrate 1, admin 1, psql 2) + superuser_reserved (3) ≤ max_connections`.
   Today: 2×16 + 3×16 + 16 + 16 = 112 + 4 + 3 = 119 > 100. Proposed: api 2×20, resolver 3×3, relay 1×2, sidejobs 1×8 → 59 + 7 = 66.
   Leave headroom for one extra api replica during a rolling deploy (S1): +20 → 86.
5. PgBouncer in transaction mode is compatible with `pg_advisory_xact_lock` (transaction-scoped) and `SET LOCAL`. It's **incompatible** with session-level
   state: `LISTEN`, session advisory locks (an S2 shard lease would be one!), and prepared statements unless configured. Add it when replicas × pool no longer fit,
   not before.

Grading: they must find the SMTP-inside-transaction holder. The alert must be on `waiting > 0` (queueing), not on `total == max` (which is normal under load).
