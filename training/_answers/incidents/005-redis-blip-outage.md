# ANSWER: INC-005 Redis blip becomes a total outage

**Verification:** RUN-VERIFIED. `tools/sim/redis-outage.ts` fails on the branch (`Server did not start without Redis`) and passes on `main` (27 s; one cold
failure first). Manual run: `/api/health` → 500 with `ClientOfflineError`, recorded as `route="/api/health",status="500"`.

## Mechanism

- `redis.ts` creates the client with `disableOfflineQueue: true`, so `redis.ping()` rejects immediately while disconnected (`ClientOfflineError`).
- `/api/health` now returns 500 on **every** API instance at the same moment. Redis is a *shared* dependency, so the failure is perfectly correlated.
- Callers of `/api/health`:
  - Caddy `reverse_proxy … health_uri /api/health, health_interval 10s` (`infra/Caddyfile`) marks every upstream unhealthy → `no upstreams available` →
    502 for everything, including the SPA (served by the same `api` process via `@fastify/static`).
  - The compose `healthcheck` (every 15 s) marks containers unhealthy. Compose doesn't restart on unhealthy, but anything keyed on health (the `edge`
    `depends_on`, a future orchestrator) reacts.
  - `tools/sim/redis-outage.ts`, `tools/sim/load.ts` and `tools/wait-ready.mjs` use it as "is the server ready?".
- Nothing about gameplay needed Redis: commands, state reads and the resolver all run on Postgres. Rate limits fall back to `rate_buckets`
  (`takeLimit`), and the relay just waits (`if (!redis.isReady) return`). The PR turned a degraded-but-correct state into an outage.

## Health model (the design answer)

| Probe | Question | Checks | Used by |
|---|---|---|---|
| **liveness** `/api/health/live` | Is this process wedged? | event loop responds; not deadlocked | container restart policy |
| **readiness** `/api/health/ready` | Should *this instance* get traffic? | local things: DB pool can get a connection within 1 s, migrations verified at boot, not shutting down (`closing` flag in `index.ts`) | Caddy `health_uri` |
| **status** `/api/health/details` (auth or internal) | What's degraded? | Redis ready, relay backlog, side-effect backlog, version | humans, dashboards, metrics |

Rule: remove an instance from rotation only for failures that are **local to that instance**, or where serving is worse than not serving. A shared
dependency that fails for every instance must degrade features (no live hints, DB-backed rate limits), not availability. Expose that as a metric
(`warband_dependency_up{dep="redis"}`) and alert on it separately.

Even the DB check deserves care: if Postgres fails over for 30 s, readiness on every instance fails together. That's arguably right (nothing works
without the DB), but pick it deliberately. Caddy's passive health (`fail_duration`) plus a `lb_try_duration` smooths short blips.

## Why ApiErrors fired but misled

The app only sees requests that reach it. During the outage, player traffic stopped at Caddy (502 generated by the edge, not counted in
`warband_http_request_seconds`). What *did* reach the app were health probes: Caddy every 10 s per instance plus docker every 15 s, all returning 500.
So close to **100 % of the measured 5xx were probes and ~0 % were players**, while real impact was 100 %. Fixes: exclude `/api/health*` and `/metrics`
from the SLI (`route!~"/api/health.*|/metrics"`), and measure availability at the edge (Caddy `metrics` directive or a blackbox probe).
The `clamp_min(…, 1)` denominator also means that under 1 request/s the ratio is under-stated. At night that matters.

## Flaky-test culture

- Cause of the real flake: `redis-outage.ts` gives the server 240 × 500 ms (plus up to 2 s per fetch) to start. On a cold machine, tsx compilation plus
  fresh migrations can exceed it. Observed here: the first run on `main` failed, and the next two passed in 27 s.
- Make the drill deterministic: separate the startup budget from the assertion, print the child's stdout/stderr on failure (today `stdio: 'ignore'`
  hides the reason), and pre-migrate the DB in a setup step.
- Policy: a required check can't be bypassed with "it's flaky". A flaky test gets an owner, a ticket and a quarantine label within a day. Merging over
  red needs the failure log *and* an explanation of why this failure isn't this PR. Here the failure message named exactly the behaviour the PR changed.

## Postmortem (short)

**Impact:** 100 % HTTP unavailability for about 2 min during routine Redis maintenance.
**Trigger:** the "deep health" PR added `redis.ping()` to the endpoint Caddy uses for routing.
**Contributing:** liveness, readiness and dependency status conflated in one endpoint; the error SLI dominated by probe traffic; a red chaos test overridden as "flaky".
**Actions:** split the health endpoints; Redis status as a metric + warning alert; edge availability SLI; drill prints diagnostics; no merge-on-red policy.
